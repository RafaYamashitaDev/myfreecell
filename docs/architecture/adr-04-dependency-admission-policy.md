# ADR-04: Dependency-admission policy

Status: Accepted

Date: 2026-11-06

## Context

Version one stays deliberately limited. Analytics, advertising, accounts, cloud services, and backend services are outside the [product specification](../product/product-spec.md). Runtime plugins should support Android and iOS unless an explicit exception is reviewed and approved, as recorded in [ADR-01](adr-01-framework-and-platform-targets.md). The domain package boundary is [ADR-03](adr-03-repository-structure-and-domain-isolation.md).

## Decision

1. Every runtime dependency requires explicit proposal, review, and owner approval before addition.
2. Cursor may research and recommend dependencies but cannot add or replace them silently.
3. Standard Flutter and Dart capabilities are preferred when they satisfy the requirement cleanly.
4. A package is admitted only when it removes meaningful risk or complexity.
5. Runtime candidates must be evaluated for necessity, alternatives, platform support, maintenance, privacy, permissions, transitive dependencies, license, and exit cost.
6. Runtime plugins should support Android and iOS unless an explicit isolated exception is approved.
7. The pure-Dart domain package starts with no third-party production dependencies.
8. Development-only dependencies receive a lighter review unless they affect production architecture, generated source, native tooling, or release builds.
9. Dependencies generated by the Flutter scaffold may be retained provisionally but must be inventoried during scaffold verification.
10. Dependency versions and the application lockfile will be managed for reproducibility; major upgrades require explicit review.
11. Approval is specific to a package, purpose, usage boundary, and version range.
12. Analytics, advertising, accounts, cloud services, backend SDKs, and unrelated platform targets remain outside scope and cannot be admitted through the dependency process.

## Consequences

- Research and recommendation are allowed, but silent dependency changes are not.
- An approval covers one package, one purpose, one usage boundary, and one version range.
- Scaffold-generated dependencies are provisional until they are inventoried.
- The domain package starts with no third-party production dependencies.

## Deferred or not decided

No concrete package or version range is approved by this ADR.
